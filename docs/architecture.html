ScoreboardCtrl

Pico W firmware for a GameCraft SK2229R. The Pico is the access point, the button driver, and the phone UI. This page is the update path: how a clock tick or a score tap becomes a digit on the phone.

Join Scoreboard and open http://192.168.0.1/. Pins, flash map, and the HTTP list live in the README.

Shared state is ScoreboardState behind one mutex. Home and away exist only there. UART does not carry scores. On hardware, time and running follow UART only: a GPIO pulse does not write running.

Update / event flow

The phone does not sample the second. It holds GET /api/events and paints each snapshot as the Pico writes it. GET /api/status is the same JSON, once, for scripts and for the fallback poll.

1. Something visible changesA new MM:SS, running, home, away, or the LED.
↓
2. publishCompares that tuple with announced. Same tuple: no wake. Duplicate UART frames of the same second stay quiet.
↓
3. WatchEVENTS is an embassy_sync watch of (). The signal means “read the mutex.” Waiters always copy the latest state, so two ticks during one slow write collapse to the newer snapshot.
↓
4. SSE writeEach stream task locks the state, refreshes running, and writes event: status plus the JSON. Then it flushes. Nagle is off, so the small packet is not held for the next ACK.
↓
5. PhoneEventSource('/api/events') parses status and updates the clock, scores (unless a score tap is in flight), the mode badge, and the running line.

Who calls publish

Clock, hardwareread_serial → set_clock only moves last_change when MM:SS actually changes, then refresh_running → publish.
Clock, simulatetimer_task decrements once a second and uses the same set_clock.
Scores and LEDboard_task updates home, away, or led and calls publish. The physical board is pulsed after the Pico value changes.
Stoppedrunning is true only while MM:SS is not 00:00 and it changed less than 2 s ago. The stream arms a timer for that deadline. heartbeat_task refreshes on its own loop too. Either path publishes the flip to stopped.

One stream, per phone

  1. On connect, the handler takes a watch receiver. Four receivers exist (MAX_EVENT_STREAMS). A fifth gets 503 busy and the TCP connection closes.
  2. The handler drops any signal from before this socket, writes one live snapshot, then waits.
  3. The wait ends on a watch wake, on a 10 s keepalive comment (:), or on the 2 s stop deadline while the clock looks running.
  4. The phone’s EventSource reconnects by itself (browser default, about 3 s). The first event after connect is a full snapshot, so a reconnect does not blank the clock.
  5. While the stream is not OPEN, index.html polls GET /api/status every 350 ms. The first status event stops that poll.

Each open stream holds one of the 12 web_task workers until the phone drops or the socket’s 60 s receive timeout fires. Four streams match the CYW43439 station cap and leave workers for score posts, captive-portal probes, and OTA. Other routes still send Connection: close after one response.

JSON on the wire

Same object for /api/status and for each status event:

{"time":"07:29","running":true,"home":1,"away":0,"led":false,"sim":false,"ver":"0.4.1","git":"abc1234","date":"2026-09-10","age_ms":40}

age_ms is how long the current MM:SS has been unchanged. 00:00 and “unchanged ≥ 2 s” are both running: false.

Control flow

Taps go the other way. They do not wait for the event stream.

Phone POST/api/ctrl/…, /api/timer/set/{min}/{sec}, or /led/on|off. Score buttons paint the new number immediately and ignore stream scores until that POST finishes.
↓
Command channelThe route enqueues a Command and returns OK. board_task is the only task that pulses pins.
↓
GPIO, 50 msStart/stop is GP1, a toggle. Hardware pulses it only when UART running (or a pending desired state from a recent pulse) disagrees with the request. A second /start before the next UART tick does not pulse again. /api/timer/set stops a running clock before the min/sec pulse train.
↓
Back through the event pathScores and the LED publish as soon as the Pico value changes. The clock publishes only when a later UART frame (or the simulate tick) shows the new MM:SS.

What stays off this path

  • Captive portal: unknown GETs 302 to the UI. After the UI has been served, Apple hotspot probes get the Success page.
  • OTA: POST /api/ota writes the DFU slot and soft-resets. It is not a scoreboard event. See the README flash map. ACTIVE must stay under 896 KiB.
  • examples/uart-test.rs is a separate image: USB CDC plus UART1, no AP and no events.

Source of the stream is EventsService and ScoreboardState::publish in src/main.rs. The phone side is the EventSource block at the bottom of index.html, which is compiled into the firmware.
